# #352 — Range report format

> **Status:** Current, owner direction 2026-10-18. Binding format for every range
> report (`ranges/range-NNN.md`), generated by `report.mjs` and enforced by
> `report.mjs check` (SPEC §3, rules F1–F8). It supersedes
> [REPORT_OVERVIEW.md](REPORT_OVERVIEW.md), whose Overview tables live on here as
> §2 Activity. Worked examples, with simulated numbers:
> [ranges/EXAMPLE.md](ranges/EXAMPLE.md). Reports committed before this format
> stay as they are (F2); the format starts with the next range played, and
> STATS.md backfills earlier ranges from their metrics.

## 1. Shape

A report is a **front** for people and an **appendix** for the fixer and builder.
Nothing is dropped; detail moves to the appendix.

| Part | Answers |
| --- | --- |
| **Headline** | Is it right? How big? How efficient? How fast? How far along? |
| **1. Correctness** | Does LayerFS match git, the plan and the native tests? |
| **2. Activity** | What did the agents do: calls, steps, Branches, conflicts, Workspaces, execs |
| **3. Storage** | What it costs on disk, what is inside, what this range added |
| **4. Speed** | Key operations, the slowest, scaling, health |
| **5. Findings and action** | Problems found, fixes, before/after, open issues, the lead's note |
| **Appendix A–G** | Checks, latency by class, probes, storage internals, stage times, attempts, evidence |

## 2. Headline

```
# Range NNN · **<verdict>** · attempt K
**Matches git ✓|✗** · daemon `<id12>` · image `<id8>` · plan vN · <continued from rNNN | forked from snapshot rNNN | rebuilt>
dsh `<first>`..`<last>` · **N commits** (M mainline, S side) · <first date> → <last date>
Areas changed: <top 3 areas by changed bytes, with share> · other
| Latest version | Store on disk | Space amplification | Added this range | Commits | Time |
**Checks:** n pass · n watch: <names and values> · n optimize/stop: <names>
**Moved most:** <top 3 movers vs previous range and baseline, ▲/▼ with %>
**Budget:** <k of 202 ranges> · projected total <h> (budget <h>) · disk <%> of budget at range 202
```

## 3. Sections

### 1. Correctness (one table)

Tree vs git (files checked, changed paths checked) · history as planned · steps
n/n · conflicts planned hit and **unplanned** · unit tests equal/run, skipped by
reason · ignored files (`node_modules` vs lockfile, build outputs) · milestone
proof (restored, oracle, `quick_check`) when the range is a milestone.

### 2. Activity

Totals line: calls · steps · agents + lead · Branches + main · Workspaces (one-shot
share, open at end). File changes: added, modified, deleted, bytes written, **fs :
Sandbox** against the ~9 : 1 target. Execs: JS vs shell, non-zero exits, installs,
builds, test runs. Then four tables, exactly as in REPORT_OVERVIEW.md §2:
**Calls by category**, **Branches**, **Conflicts** (with the Unplanned row),
**Agents** (steps by category, Commits, conflicts).

### 3. Storage

Previous vs now vs change: latest version (tracked / `node_modules` / build) ·
files, directories, symlinks · largest file and directory · **Store on disk
(allocated)** · **space amplification** · content amplification · compression ·
metadata share · **stored per byte changed** (with × median) · history totals
(Commits, Layers, Branches) · projection at range 202 against the disk budget ·
snapshot taken.

**What's inside:** per object role (whole files, large files, chunks,
directories, inodes and attributes, symlinks): total, added, average size,
reused (dedupe hits), share stored as delta. One line for delta depth (at cap,
stopped by budget) and the `node_modules` reinstall gate; one line for added
bytes by source (tracked, `node_modules`, build, metadata, history).

### 4. Speed

Key operations p50/p95 with the ratio to baseline: write, read, list, one-shot
Commit, mount, merge, exec (FUSE ÷ native). SQL statements p50 under each. Commit
cost per changed file; one-shot Workspace total. The three slowest, each with its
input size. Scaling: probes flat out of total, and every non-flat one by name.
**Health:** Workspaces open, overlay files left, daemon memory (change), open
files, WAL before seal.

### 5. Findings and action

- **No problem found:** one line, `**Optimization:** none — no problems found.`,
  then the lead's note (watch items and their planned probes). Nothing else.
- **A finding (optimize or stop), per attempt that tripped:**
  1. **Trigger:** check, value, threshold, binary.
  2. **Fix context:** playbook step; the cause in code; the old design and the
     new design in one line each; fix kind (code path, data written, Store
     format); commits; regression tests; recovery (fork, rebuild, rerun).
  3. **Before / after:** the same measures on the same snapshots, old binary vs
     new: measure · before · after · change · old binary · new binary · snapshot
     or checkpoint · cache. Counter exponents before → after.
  4. **With vs without the optimization, this range:** the attempt that tripped
     against the rerun, side by side on the headline numbers (time, key
     operation p50/p95, SQL per call, Store on disk, space amplification), each
     column labeled with its binary. Never merged into one series.
  5. **Cost of the fix:** what got slower or bigger (for example statements per
     Commit, bytes per hint row), stated even when small.
  6. **Records:** links to every `fixes/NNN-aK-<slug>.md` and the BUGS.md or
     OPTIMIZATIONS.md line.
  Until the fixer's finding exists: `Diagnosis pending: finding-NNN.aK.json`.
- **Open issues:** every open finding that touches this range (id, one line,
  owner, next step), whether or not it tripped a gate here.
- **Lead's note:** never empty unless the verdict is pass.

## 4. Names (user-facing)

| Name in the report | Definition |
| --- | --- |
| Latest version | Raw bytes of every file at the checkpoint as LayerFS sees it (tracked + `node_modules` + build), uncompressed |
| Store on disk | Allocated bytes of the sealed Store file |
| **Space amplification** | Store on disk ÷ latest version |
| Content amplification | Stored content bytes ÷ latest version |
| Compression | Canonical ÷ stored |
| Metadata share | Metadata bytes ÷ Store on disk (this range: ÷ added) |
| Stored per byte changed | Added this range ÷ bytes git changed in the range |
| Added this range | New stored bytes: content + metadata + history |
| Reused | Objects the range touched that were already stored |
| Sum of Commit trees | (appendix only) the old "logical"; never shown as raw size |

## 5. Appendix

A. All checks with values and thresholds · B. Latency by method and size class,
×baseline, depth and tree slopes, SQL and FUSE counters · C. Scale probes with
counters · D. Storage internals: bytes per SQLite table and index, free pages,
packs, depth and chain histograms per role (from the sealed file at snapshots,
stating which snapshot) · E. Stage times · F. Attempts (frozen, F2) · G. Evidence
paths.

## 6. Sources

| Numbers | Source |
| --- | --- |
| Added objects by role, deltas, reuse | per-call `delta` and storage counters in the trace |
| Store totals | `operator.store.stats`, recorded per range |
| Latest version, files, directories, largest | the checkpoint tree listing (verify walks it) |
| Totals by role, average sizes, SQLite internals | `inspect.mjs stats` on the sealed file, at snapshots |
| Allocated bytes | the sealed file's allocation on disk |
| Previous values | the previous range's metrics file, never recomputed |
| Before / after | `finding-NNN.aK.json` (findings.mjs) |

## 7. Checks added to `report.mjs check`

All of REPORT_OVERVIEW.md §3, plus: the headline has every field; sections 1–5 and
the appendix exist in order; §5 is the one-line "none" form or has every finding
part (1–6) or "Diagnosis pending"; every open finding touching the range is
listed; with-vs-without columns name different binaries; space amplification
equals Store on disk ÷ latest version within rounding.

## 8. As built (builder, 2026-10-18)

`dsh/tools/history/format.mjs` renders this format and holds §7's checks
(`checkFormat`, run by `report.mjs check` under F1); `run.mjs` records the
measurements. Where a number cannot come from the named source yet:

- **Latest version** is LayerFS's own walk of the published tree (one exec in a
  one-shot Workspace every range, `lstat` only, the probe fixture left out).
  Its tracked part is git's (the tree was just proved equal); `node_modules` is
  every path under a `node_modules` folder; build is the rest.
- **Store on disk** is the sealed file's allocation at snapshots; at other
  ranges it is the live file plus its WAL, marked `live`.
- **What's inside:** totals and average sizes come from the sealed file at
  snapshots (`— (at snapshots)` otherwise). Directories and inodes are one
  pooled metadata role in the trace, so their Added sits on the Directories
  row. No trace counter counts dedupe hits; Reused on whole files is derived
  (files constructed − unchanged − new whole-file objects) and labelled so.
- **Open issues** are every open BUGS.md finding (`- **F-NNN · title …**`,
  without **Fixed**/**Closed**); owner and next step come from its "Owner:
  who, next step." sentence.
- **With vs without** is generated from the tripped attempt's and the rerun's
  metrics; the fixer's finding adds `design: { old, new }` and `cost`
  (findings.mjs), required for findings reported in this format.
- **Stage times** (appendix E): play includes the runner's prepare (binary and
  disk checks, the Sandbox pool); verify includes the latest version's walk;
  seal + snapshot includes the sealed file's figures; report includes the
  metrics and health reads.


- **Open issues are judged as of the attempt** (F-021 follow-up, lead
  decision 2026-10-18; F2). The §7 check requires only the BUGS.md findings
  open now that were opened (first committed, `git log -S`) by the latest
  attempt's `started` time in its metrics; one opened later, or not yet
  committed, is not required in an earlier report.
