## 1. Shape

A report is a **front** for people and an **appendix** for the fixer and builder.
Nothing is dropped; detail moves to the appendix.

| Part | Answers |
| --- | --- |
| **Headline** | Is it right? How big? How efficient? How fast? How far along? |
| **1. Correctness** | Does LayerFS match git, the plan and the native tests? |
| **2. Activity** | What did the agents do: calls, steps, Branches, conflicts, Workspaces, execs |
| **3. Storage** | What it costs on disk, what is inside, what this range added |
| **4. Speed** | Key operations, the slowest, scaling, health |
| **5. Findings and action** | Problems found, fixes, before/after, open issues, the lead's note |
| **Appendix A–G** | Checks, latency by class, probes, storage internals, stage times, attempts, evidence |

## 2. Headline

```
# Range NNN · **<verdict>** · attempt K
**Matches git ✓|✗** · daemon `<id12>` · image `<id8>` · plan vN · <continued from rNNN | forked from snapshot rNNN | rebuilt>
dsh `<first>`..`<last>` · **N commits** (M mainline, S side) · <first date> → <last date>
Areas changed: <top 3 areas by changed bytes, with share> · other
| Latest version | Store on disk | Space amplification | Added this range | Commits | Time |
   (Space amplification cell: total, then `tracked <x>×` whenever `node_modules` or build bytes exist, then prev)
**Checks:** n pass · n watch: <names and values> · n optimize/stop: <names>
**Moved most:** <top 3 movers vs previous range and baseline, ▲/▼ with %>
**Budget:** <k of 202 ranges> · projected total <h> (budget <h>) · disk <%> of budget at range 202
```

## 3. Sections

### 1. Correctness (one table)

Tree vs git (files checked, changed paths checked) · history as planned · steps
n/n · conflicts planned hit and **unplanned** · unit tests equal/run, skipped by
reason · ignored files (`node_modules` vs lockfile, build outputs) · milestone
proof (restored, oracle, `quick_check`) when the range is a milestone.

### 2. Activity

Totals line: calls · steps · agents + lead · Branches + main · Workspaces (one-shot
share, open at end). File changes: added, modified, deleted, bytes written, **fs :
Sandbox** against the ~9 : 1 target. Execs: JS vs shell, non-zero exits, installs,
builds, test runs. Then four tables, exactly as in REPORT_OVERVIEW.md §2:
**Calls by category**, **Branches**, **Conflicts** (with the Unplanned row),
**Agents** (steps by category, Commits, conflicts).

### 3. Storage

Four tables, in this order. Every ratio is against the **latest version** (raw
head bytes), as the owner set; §9 has the formulas.

**3a. Overview** (previous · now · change): latest version (tracked /
`node_modules` / build) · files, directories, symlinks · largest file and
directory · **Store on disk (allocated)** · **space amplification**, total and
per source · **head cost** and **history cost** (at snapshots; `— (not at a
snapshot)` otherwise) · **stored per byte changed**, split content / metadata /
shared (with × median) · **stored per Commit** · metadata share · history totals
(Commits, Layers, Branches) · projection at range 202 against the disk budget ·
snapshot taken.

**3b. Where the bytes are** (parts that add up to Store on disk):

| Content | | | |
| Metadata | | | |

| Other | | | |

Exact at snapshots (from the sealed file). At other ranges the parts come from

**3c. By source:**

A source with no bytes shows `0` and `—` for its ratios. Any comparison with git

**3d. What's inside:** per object role (whole files, large files, chunks,

reused (dedupe hits), share stored as delta. One line for delta depth (at cap,
stopped by budget) and the `node_modules` reinstall gate.

### 4. Speed

Key operations p50/p95 with the ratio to baseline: write, read, list, one-shot
Commit, mount, merge, exec (FUSE ÷ native). SQL statements p50 under each. Commit
cost per changed file; one-shot Workspace total. The three slowest, each with its
input size. Scaling: probes flat out of total, and every non-flat one by name.
**Health:** Workspaces open, overlay files left, daemon memory (change), open
files, WAL before seal.

**Speed as history grows** (owner 2026-10-19, ranges 18 on, P3; a watch row,
never a gate, workload, timeout or cache change; `growth.mjs`). Range 15 is the
reference.
- **Trend:** one row per range from 15, with Commits and Store MiB. For each
  tracked uncontended class (`fs.write` ≤1/≤8/≤64 KiB, `fs.read` ≤8 KiB,
  `sandbox.mount`, `sandbox.commit` 1 file Committed, `branch.merge`) it shows
  p50 (× range 15), VM steps and read syscalls per solo call.
- **Read syscalls stand in for page-cache misses.** The binary reports no
  SQLite page-cache hit/miss counter, but SQLite reads a missing page with one
  `pread`. A call's `/proc/self/io` delta (`syscr`, `rchar`, `read_bytes`)
  belongs to the call only when no other recorded call overlapped it ("solo").
  Workspace calls read in the daemon's process, so they show none.
  Ranges 15–17 have no counters ("not recorded").
- **WAL:** its size at each class's first and last call this range.
- **Host load:** macOS 1-min load from `runs/<id>/hostload.jsonl`, which
  `runner.mjs` writes around each command, and the Docker VM's.
- **Control probe** (`control.mjs`, `metrics/control-NNN.a<attempt>.json`):
  - One sample per arm, in one command, with the same binaries.
  - Each arm runs 15 `fs.write` ≤1 KiB, 15 `fs.write` ≤8 KiB and 15 `fs.read`
    ≤8 KiB calls in its own fresh volume:
    - (a) a clone of the range 15 terminal Store;
    - (b) a clone of the range's Store.
  - The table shows each arm's p50, (b)/(a), (a) against its first completed
    sample, and read syscalls per call.
  - If both arms slow together, the host is the cause; if only (b) slows,
    history growth is.
  - Gap: the clone copy warms the OS cache equally in both arms, so the
    control cannot see a cold-read effect of a larger Store. The section says
    so.
- **Watch row:** fires when this attempt's control (b)/(a) p50 is over 1.25×,
  or (b)'s read syscalls per call are over 2× (a)'s. A sample with failed calls
  is listed but not judged. Labelled samples, such as
  `control-017.diag-15v17-2`, are diagnostics.

### 5. Findings and action

- **No problem found:** one line, `**Optimization:** none — no problems found.`,
  then the lead's note (watch items and their planned probes). Nothing else.
- **A finding (optimize or stop), per attempt that tripped:**
  1. **Trigger:** check, value, threshold, binary.
  2. **Fix context:** playbook step; the cause in code; the old design and the
     new design in one line each; fix kind (code path, data written, Store
     format); commits; regression tests; recovery (fork, rebuild, rerun).
  3. **Before / after:** the same measures on the same snapshots, old binary vs
     new: measure · before · after · change · old binary · new binary · snapshot
     or checkpoint · cache. Counter exponents before → after.
  4. **With vs without the optimization, this range:** the attempt that tripped
     against the rerun, side by side on the headline numbers (time, key
     operation p50/p95, SQL per call, Store on disk, space amplification), each
     column labeled with its binary. Never merged into one series.
  5. **Cost of the fix:** what got slower or bigger (for example statements per
     Commit, bytes per hint row), stated even when small.
  6. **Records:** links to every `fixes/NNN-aK-<slug>.md` and the BUGS.md or
     OPTIMIZATIONS.md line.
  Until the fixer's finding exists: `Diagnosis pending: finding-NNN.aK.json`.
- **Open issues:** every open finding that touches this range (id, one line,
  owner, next step), whether or not it tripped a gate here.
- **Lead's note:** never empty unless the verdict is pass.

## 4. Names (user-facing)

| Name in the report | Definition |
| --- | --- |
| Latest version | Raw bytes of every file at the checkpoint as LayerFS sees it (tracked + `node_modules` + build), uncompressed |
| Store on disk | Allocated bytes of the sealed Store file |
| **Space amplification** | Store on disk ÷ latest version; the sum of the five parts (§9) |
| Content · Metadata · Index rows · Waste · Other | The five parts of Store on disk (§9), each also shown ÷ latest version |
| Amplification (per source) | Stored content + metadata attributed to the source ÷ the source's latest version |
| Shared | Index rows + waste + other: real cost, never divided among sources |
| Head cost | Stored bytes needed to read the latest version alone ÷ latest version (snapshots) |
| History cost | Space amplification − head cost |
| Metadata share | Metadata ÷ Store on disk (this range: ÷ added) |
| Stored per byte changed | Added this range ÷ bytes changed in the range, split content / metadata / shared |
| Stored per Commit | Added this range ÷ LayerFS Commits in the range |
| Added this range | New stored bytes written this range (trace counters): content + metadata + shared rows, split by source. Not the allocated growth, which also moves with WAL and free pages |
| Compression | (appendix only) canonical ÷ stored; counts every version, so it is not a disk measure |
| Reused | Objects the range touched that were already stored |
| Sum of Commit trees | (appendix only) the old "logical"; never shown as raw size |

    pages (Waste). Other is the remainder; it is 0.6% of the latest version at

  - **Live ranges.** Content and metadata are the previous range's plus this

    specified for the fixer in the builder's notes.
  - **Seeding.** Cumulative figures start at the first sealed snapshot, with
    everything stored before it counted as tracked.
  - **Unattributed.** Saves with no traced sizes (a merge's new Commit)
    appear on an Unattributed row, so the column still sums to Store on disk.
  - **Head cost** reads `— (needs a reachability walk of the sealed file;
    not built)` until that walk exists, so history cost is not reported yet.
  - **Changed bytes per source.** Tracked is git's changed bytes;
    `node_modules` is the package folders that the lister finds added or
    rewritten against the previous install; build is the built packages'
    output bytes.
  - **Compression** moves to appendix D. Content amplification is gone.
  - **§7 checks** (`storageProblems`, in `checkFormat`) run on the recorded
    figures:
    - the parts sum to Store on disk exactly, and to space amplification
      within rounding;
    - sources + unattributed + shared = Store on disk;
    - per-source latest versions sum to the total;
    - 3a–3d and the Shared row are present;
    - a git comparison names the Tracked row.

## 9. Storage formulas (owner direction 2026-10-18)

All ratios divide by the latest version, the raw bytes of the head (per source
for per-source ratios).

```
Space amplification = Store on disk ÷ latest version
                    = (Content + Metadata + Index rows + Waste + Other) ÷ latest version

Content    = stored body bytes of payload-domain packs (file data: whole files,
             chunks, deltas, every version)
Metadata   = stored body bytes of metadata-domain packs (directories, inodes,
             attributes, file states, extent trees)
Index rows = used bytes of every row table and index other than pack bodies:
             object_location, commit, commit_identity, inode_value, binding_hint,
             content_signature, branch*, layers*, history_meta, …
Waste      = unused bytes inside allocated pages + free pages + pack row overhead
             (pack table used bytes − pack body bytes) + file allocation beyond
             page_count × page_size
Other      = Store on disk − the four above (schema and anything unlisted); a
             large Other is a tooling defect to fix, not a part to explain away

Amplification(source) = (Content(source) + Metadata(source)) ÷ latest version(source)
   source ∈ { tracked, node_modules, build }
   an object belongs to the source of the path it was constructed for:
   under a node_modules/ folder → node_modules; a build output path → build;
   anything else (including every ancestor directory) → tracked
Shared = Index rows + Waste + Other   (shown, never divided among sources)

Head cost(source)   = stored bytes of objects reachable from the head root under
                      that source, plus delta bases needed to read them,
                      ÷ latest version(source)                    (at snapshots)
History cost        = Space amplification − Head cost

Stored per byte changed = Added this range ÷ bytes changed this range
   (per source; split content / metadata / shared)
Stored per Commit       = Added this range ÷ LayerFS Commits this range
```

Why: the head-based ratio rises with history even when storage is perfect, and
`node_modules` (P3 on, ~224 MB raw at range 4) would pull the total below 1×
and hide the tracked files' overhead. The parts say what is data and what is
overhead; the per-source rows keep tracked overhead visible; head cost separates
the floor from history; the per-change figures expose waste without the drift.

Range 011 in this shape (sealed snapshot): Store on disk 32.8 MiB on a 7.7 MiB
latest version (tracked only) = **4.26× = content 1.10 + metadata 1.35 + index
rows 0.98 + waste 0.82 + other 0.01** (exact parts from the sealed file,
STORAGE_STUDY.md §2; an earlier rough split here said index 1.07, waste 0.69);
stored per byte changed 1.78 (content 0.78, metadata 1.00); stored per Commit
6.8 KiB. Expected ranges per part and per Commit, and defect signatures:
[STORAGE_STUDY.md](STORAGE_STUDY.md).

**Absolute time floor (owner 2026-10-20).** `THRESHOLDS.absoluteFloorMs = 5`.
A time row trips only when its ratio is over the band **and** the extra time
per call is over 5 ms, at p50 and, for a p95 trip, at p95. This covers Speed
against the baseline, the time Scaling fits and the chain bound's ms side
(judged on the whole call; a per-entry fit on its total), time-only trips, and
the control probe's watch row in "Speed as history grows". Below the floor the
row passes and reads "under the 5 ms floor (+x ms per call)". Counter gates,
storage, correctness, Node and wall/budget rows are unchanged. Reports
recorded before the rule keep their rows (F2).

### 10.4 Baselines and trends

- **Speed baselines** are already phase-matched (`baselineFor`): a P3 attempt
  is compared only with a P3 re-baseline (`run.mjs rebaseline --phase p3`,
  HANDOFF), never with the P2 or P1 baseline. Until one exists, Speed is
  `not judged` and the Git and Node table says so.
- **Moved most** keeps its existing measures; the git and Node rows join it
  only after three P3 ranges exist (not built yet; until then they are never
  movers).
- The first P3 report's lead note states that its storage and speed figures
  start a new series.

### 10.5 `report.mjs check` for P3

On a P3 attempt, `checkFormat` also requires: the headline's Phase, Git, Node,
Content, Churn and Time split; the proofs subsection in §1 with a row for every
recorded point and `NOT_RUN` shown for proofs not run; the Git, Install inputs
and Conflicts by path class rows; no P2 fs : Sandbox target; Execs by tool,
3e, the Resilience line and the tracked-only line; the `.git` row in 3c when
the storage figures carry it; and appendix H, I, J after G, in order. The
storage sums of §7 include the `.git` source. A P2 attempt is checked exactly
as before.
