## Reading

- **D-9 alone** (count-driven): steady walks send no listing request at all
  (READDIR 14,322 → 0). Steady find −31%, du-s −47%, ls-r −65%. Cold walks are
  unchanged, as expected: a first listing still has to be fetched.
- **What a steady walk still pays:** the OPENDIR/RELEASEDIR pair of each
  directory (21,921 served for 7,161 directories). OPENDIR reads the
  directory's base facts, about 5 reader requests each (35,780 for find).
  These are immutable-cache misses on the same objects the cold walk read:
  the 8 MiB immutable cache does not hold the walk's working set. A
  per-directory facts window (F-A2/F-A3) or a larger immutable cache (an
  owner memory decision; v0.1.6 used 32 MiB) is what removes them.
- **READDIRPLUS on A1 + D-9:**
  - stat walks gain: du-s cold −33% (16.1 → 10.8 s), owner jobs −61%, and
    rm-rf-nm owner jobs −25% at equal time;
  - name-only walks lose: find cold +152% (4.6 → 11.7 s), ls-r cold +99%.
    Every listed entry's facts are read (about 5.5 reader requests each)
    whether or not the program ever stats it;
  - steady walks are unchanged, because D-9 already sends no listing.

  So READDIRPLUS as negotiated today (always on) is not adopted.
  `READDIRPLUS_AUTO` would let the kernel ask for plus only when it saw stats
  follow a listing. It is S8-forbidden, so it is an owner decision. It goes
  into the combo proposal.
- **#356 target** (rm -rf of 40,145 committed files in about 3 s): still
  missed, at 21.2 s in the best arm.

## Exactness: D-9 needs directory cookies that outlive their handle

With `FOPEN_CACHE_DIR` the kernel serves a listing from its cache, including
each entry's offset. Those offsets are the cookies the handle that filled the
cache was given.

The cache can be reset while another handle is reading from it. The causes
are:

- a directory change seen by the next listing from offset 0 (`iversion` or
  mtime);
- an `inval_inode`;
- reclaim of a cache page under memory pressure.

`fuse_readdir_cached` then returns `UNCACHED`, and the kernel sends READDIR on
the *reading* handle with its current position. That position is a cookie
another handle minted, and that handle may be closed already.

Today a cookie is resolved only in its own handle's store. The store is
deleted at RELEASEDIR, and pages below a rewind floor are deleted too. Such a
READDIR would fail, so the diagnostic arms are not exact. None of the samples
above hit the case: every listing completed and the comparison agreed.

The exact design, which needs the overlay `lifetime/kernel_cookie.rs`,
`kernel_directory*.rs` and `open/directories.rs`:

1. Cookies are resolved per directory. A READDIR cookie that is not in its
   own handle's store is looked up in the other stores of the same directory
   serial. Cookie numbers are unique per engine, so the lookup is
   unambiguous. A number found nowhere and below the handle's floor is still
   `Rewound`.
2. Pages are not deleted while the kernel may present them. A closed handle's
   pages, and pages retired below a rewind floor, move into the directory's
   retained store instead of being deleted.
3. Bound: when the last open handle of a directory closes and its retained
   store holds more than one listing, the daemon sends `inval_inode` for the
   directory and clears the store. With no handle open, no READDIR can be in
   flight and no position is held, so nothing can present a dropped cookie.
   The retained store is also dropped at the directory's last kernel
   reference (FORGET) and at unmount.

   Resident cost: at most one listing's names per kernel-referenced directory,
   plus the listings made while a handle on it stays open. That falls under
   the declared exception (open state grows with open files and with the
   files the kernel references). For this repository's `node_modules`
   (7,161 directories) the names come to about 1 MB.

Invalidation needs no new mechanism:

- Namespace changes through the mount bump the directory's `iversion` in the
  kernel (`fuse_dir_changed`), and the next listing from offset 0 resets the
  cache.
- A merged install already sends `inval_inode(serial, 0, 0)` for every inode
  whose leaf changed. A directory whose bindings changed has a changed leaf.
  That drops its cached listing.
- An own-root install changes nothing the kernel showed, so it sends nothing,
  as before.

The one ordering caveat is shared with the existing entry and attribute
invalidation. A reply computed before a merged install but delivered after
its invalidation is not fenced. Entry and attribute replies are bounded by
their TTL. A cached listing has no TTL, and the kernel's `iversion` check
does not cover installs. So under D-9 a stale listing could last until the
directory's next change. This is recorded as **BUGS.md F-044**, an open
finding (liaison 2026-10-18), and D-9 is not claimed exact until it is
fenced.
