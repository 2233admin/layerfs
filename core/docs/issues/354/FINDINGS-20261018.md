The three figures in fix record 015 measure different things, so they cannot be compared directly:

**Max RSS is not live heap.** It also counts allocator retention (pages the allocator keeps after a free) and SQLite's page cache: `cache_size -2048` gives 2 MiB per connection, and `mmap_size` is 0. A counting global allocator (`HeapCount`, statics `LIVE`/`PEAK`) gives the exact live-heap peak. All runs below are whole-tree grep with no match (`heap-*.log`).

| Build | P3 heap peak | Range-14 heap peak | P3 max RSS |
| --- | --- | --- | --- |
| P0 | 3.29 MB | 2.76 MB | 19.3 MB |
| P1 | 4.18 | 3.07 | 22.3 |
| P2 | 4.77 | 3.07 | 23.4 |
| P3 | 8.13 | 7.00 | 30.8 |
| P4 | 9.36 | 7.43 | 35.9 |
| P5 | 9.36 | 7.43 | 35.9 |

- **Heap after the call:** ≈1.34 MB on P3 and 1.24 MB on range 14. This is the Storage's persistent locator and descriptor caches.
- **Where the growth comes from:** the step from P2 to P3/P4 adds about 3.4 MB and 1.2 MB of heap. These are the per-call caches (`ReadCache`) and the root batch.
- **Peak against tree size:** from range 14 to P3 the tree is 32× larger by file count and the heap peak grows only about 1.9 MB. That is the profile of bounded working state, not of state that grows with the tree.
- **Most of the RSS growth is not heap.** RSS grew about 16.6 MB from P0 to P5 while the heap grew 6.1 MB. The remainder is allocator retention plus the page cache.
- **Reuse probe** (`p3-reuse.txt`, `mem-reuse-*.log`): one reader shared across all files peaks 5.4 MB above fresh readers per file. This matches the cache bounds below.

### Change made: inode-value reads without BEGIN/COMMIT (`b83871223`)

`inode_value` gets one plain INSERT per ordinal and never an UPDATE or DELETE.
That makes each `metadata::values::read` an immutable read, so it now runs
through `Session::read_immutable`: one statement instead of BEGIN + SELECT +
COMMIT.

| Call | Before (P5) | After (iv) |
| --- | --- | --- |
| P3 fs.read ×4,000 | 167,990 statements (42.0/file), 13.03 s | 115,818 (29.0/file), 6.91 s |
| P3 path lookup / file | 31.5 | 18.45 |
| Range-14 fs.read ×1,263 | 60,036 (47.5/file), 2.07 s | 51,322 (40.6/file), 1.86 s |
| Range-14 lookup / file | 30.9 | 24.0 |
| P3 grep (whole tree, no match) | 39,739 statements, 4.72 s | 32,353, 3.73 s |

- **Equivalence:** results are byte-identical to the previous build.
  - Range 14: grep, glob, list, read, and pages at page size 100.
  - P3: grep1, read (4,000 files), glob1, list.
  - The dumps are recorded by SHA-256 as `p3-iv-*` and `r14-iv-*`.
- **Times** are single macOS diagnostic samples from the `calls` probe, not qualified.
- **Object and pack counts are unchanged:** 86,118 objects and 59,481 pack selections on P3. Only BEGIN/COMMIT went away.

### What remains (not changed, recorded for #359)

After this change, path lookup is still the largest part of fs.read on P3: 18.45 of 29 statements and about 81% of probe time (`lookup` 5.62 s of 6.85 s in `fixed-split.txt`, P5).

- **Why:** each call starts with an empty `ReadCache`. It therefore re-reads the directory packs from the root to the file: 11.8 selections and 202 KB per file.
- **Possible fix:** a cache of immutable directory objects that outlives one call would remove most of that.
  - The reuse probe shows the scale: across all 40,408 files a shared reader takes 178,032 statements and 3.78 s, fresh readers 344,847 statements and 5.03 s.
  - The cost is a cache that lives across calls, and that is an owner decision about memory, so it is **held**. Nothing in this branch adds one.

## 4. Immutable autocommit: safety verification

`Session::read_immutable` runs a read without BEGIN/COMMIT. Each statement
takes its own WAL snapshot. It checks autocommit before and after, and
quarantines the session on anything uncertain.

| Read | Why it is safe | Source checked |
| --- | --- | --- |
| `object_location` (locate) | `INSERT ... ON CONFLICT(object_id) DO NOTHING`; no UPDATE or DELETE anywhere | persistence SQL and providers |
| `pack` / `pack_unit` (selection, units, body) | triggers refuse UPDATE and DELETE | schema triggers |
| pack identity | `next_pack_id` only advances (`reserve`), so a pack id is never reused | storage provider |
| `inode_value` | one plain INSERT per ordinal (a second INSERT fails); no UPDATE or DELETE | `metadata::values` |
| ordinals | `release_ordinals` gives back only an unwritten tail (compare-and-set), so a reused ordinal has no row any reader could have seen | metadata provider |
| reclamation | free pages only (`auto_vacuum=2`, `reclaim_space`); it moves pages, never rows. Callers today: tests and one benchmark example | persistence |

- **Overlap with #353:** its pushed changes mutate its own tables (merge, reach, lineage), `layer.overwrote` and `history_meta`. None of them is `object_location`, `pack`/`pack_unit` or `inode_value`.
- **Reads keep their transaction** when they pick a snapshot: Branch heads, roots, and Layer and Commit rows.

Concurrency coverage:

- `sdk_reads_under_publish` (`0b0a883f0`): paged reads of `main` stay byte-identical while another Branch publishes.
- `immutable_reads_under_reclamation` (new in `b83871223`): locates, and fresh-reader object reads, stay byte-identical while another session reclaims free pages.
  - macOS: 1,147 reclamation jobs (1,147 pages) during 95 read rounds.
  - It also passes on Linux.

## 5. Paging: count-based, held

The `nextPagePos` of fs.grep, fs.glob and fs.list is a count. Serving page j
re-walks the tree and skips the earlier items, so reading every page of R items
at page size k costs O(R²/k) walk work.

Statements on page 1 against page 100 (range 14, `r14-old-paging.txt`, `r14-new-paging.txt`):

| Call | Before #354 | Now |
| --- | --- | --- |
| grep | 408 → 720 | 595 → 521 |
| glob | 336 → 3,558 | 80 → 217 |
| list (7 pages) | 69 → 84 | 30 → 35 |

- Pruning and the per-call caches made the re-walk cheap, but did not remove it.
- Full pagination of range 14 takes 93 s at page size 7 and 11 s at page size 100. This is diagnostic and shows the quadratic term.
- The public token contract is unchanged. Resumable tokens stay held under the existing owner direction; [PAGE-CURSOR-PROPOSAL.md](PAGE-CURSOR-PROPOSAL.md) is the concrete proposal. **This item is not complete.**
