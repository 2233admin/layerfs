### What remains (not changed, recorded for #359)

After this change, path lookup is still the largest part of fs.read on P3: 18.45 of 29 statements and about 81% of probe time (`lookup` 5.62 s of 6.85 s in `fixed-split.txt`, P5).

## 4. Immutable autocommit: safety verification

`Session::read_immutable` runs a read without BEGIN/COMMIT. Each statement
takes its own WAL snapshot. It checks autocommit before and after, and
quarantines the session on anything uncertain.

| Read | Why it is safe | Source checked |
| --- | --- | --- |
| `object_location` (locate) | `INSERT ... ON CONFLICT(object_id) DO NOTHING`; no UPDATE or DELETE anywhere | persistence SQL and providers |
| `pack` / `pack_unit` (selection, units, body) | triggers refuse UPDATE and DELETE | schema triggers |
| pack identity | `next_pack_id` only advances (`reserve`), so a pack id is never reused | storage provider |
| `inode_value` | one plain INSERT per ordinal (a second INSERT fails); no UPDATE or DELETE | `metadata::values` |
| ordinals | `release_ordinals` gives back only an unwritten tail (compare-and-set), so a reused ordinal has no row any reader could have seen | metadata provider |
| reclamation | free pages only (`auto_vacuum=2`, `reclaim_space`); it moves pages, never rows. Callers today: tests and one benchmark example | persistence |

- **Overlap with #353:** its pushed changes mutate its own tables (merge, reach, lineage), `layer.overwrote` and `history_meta`. None of them is `object_location`, `pack`/`pack_unit` or `inode_value`.
- **Reads keep their transaction** when they pick a snapshot: Branch heads, roots, and Layer and Commit rows.

Concurrency coverage:

- `sdk_reads_under_publish` (`0b0a883f0`): paged reads of `main` stay byte-identical while another Branch publishes.
- `immutable_reads_under_reclamation` (new in `b83871223`): locates, and fresh-reader object reads, stay byte-identical while another session reclaims free pages.
  - macOS: 1,147 reclamation jobs (1,147 pages) during 95 read rounds.
  - It also passes on Linux.

## 5. Paging: count-based, held

The `nextPagePos` of fs.grep, fs.glob and fs.list is a count. Serving page j
re-walks the tree and skips the earlier items, so reading every page of R items
at page size k costs O(R²/k) walk work.

Statements on page 1 against page 100 (range 14, `r14-old-paging.txt`, `r14-new-paging.txt`):

| Call | Before #354 | Now |
| --- | --- | --- |
| grep | 408 → 720 | 595 → 521 |
| glob | 336 → 3,558 | 80 → 217 |
| list (7 pages) | 69 → 84 | 30 → 35 |

- Pruning and the per-call caches made the re-walk cheap, but did not remove it.
- Full pagination of range 14 takes 93 s at page size 7 and 11 s at page size 100. This is diagnostic and shows the quadratic term.
- The public token contract is unchanged. Resumable tokens stay held under the existing owner direction; [PAGE-CURSOR-PROPOSAL.md](PAGE-CURSOR-PROPOSAL.md) is the concrete proposal. **This item is not complete.**

## 8. inode_value is insert-only (the safety argument's evidence)

`inode_values` runs without BEGIN/COMMIT only because `inode_value` rows never
change once written:

- **Writes:** one plain INSERT per ordinal at publish. A second INSERT of the same ordinal fails, and the whole batch is refused (`a_stored_value_is_never_replaced_and_a_refused_batch_leaves_no_row`).
- **No production UPDATE or DELETE** exists. The only ones are the test's deliberate corruption at `sqlite_inode_values.rs:196` and `:207`. The liaison checked `dsh-history-replay` and `issue360-storage` and found none either.
- **Ordinal give-back:** `release_ordinals` gives back only a tail with no row written, so no reader can have seen a reused ordinal's row.
- **Missing ordinals behave as before.**
  - At the port, an ordinal with no row is omitted: `values_come_back_in_ordinal_order_from_one_statement_of_one_transaction`, lines 74–85.
  - A leaf read whose row is missing still fails with "metadata ordinal missing": `a_row_changed_in_the_file_fails_the_read_of_its_leaf`, lines 205–215.
  - Both run through the new route.
- **Revisit trigger:** any change that updates or deletes `inode_value` rows makes this unsafe. That includes #360 item 3 (inode branches as deltas) and any future GC. Such a change must move `inode_values` back into a transaction.
- **Commit order:** `b83871223` follows the item-3 commit `0b0a883f0`, with only the docs commit `337bf0024` between them. It can be dropped together with `0b0a883f0`, or on its own.
- **The exact-count test** `sqlite_inode_values` changes from 3 statements and 1 transaction to 1 statement and 0 transactions. The assertion is updated to the new behaviour, not weakened.
