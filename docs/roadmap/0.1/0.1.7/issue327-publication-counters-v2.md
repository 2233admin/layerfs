# #327 publication counters: matched component screen v2

> **Status:** Prospective component screen specification, 2026-10-15. Issue
> [#327](https://github.com/Ephemeral-AI-Lab/layerfs/issues/327) owns this work.
> This is not an SDK/FUSE performance or release qualification.

The uncommitted `issue327_counters` example was an unexecuted harness prototype:
its first build failed on the open API, and the corrected build succeeded. It
collected no sample. The v2 executable and runner are finalized only after this
specification is committed. No v1 sample exists to promote or replace.

## Question and arms

`issue327-publication-totals-v2` asks what the SQL maintenance of publication
counters costs in time and allocated Store bytes. There are exactly two arms,
one invocation per arm, in this order: `off`, then `on`. Both arms use the same
new history/schema/commit-v3 format, per-Commit statistics, construction and Save
code. `off` is an experimental source ablation removing only the Store-totals
UPDATE in storage publication and the logical-total UPDATEs in history insertion.
It is never merged into the product. Neither arm branches on scenario identity.

Each source is frozen as a Git tree/commit and a compilation/source manifest
before execution. Record the complete ablation patch, first-party and dependency
identities, Cargo lock and Rust/Cargo versions, ARM64 build inputs, system SQLite
version, binary SHA-256 and harness hash. Release only, locked Cargo +1.85.1;
worktree-local targets and locks. No concurrent owned build or measurement during
either arm. Record other observed interference without interrupting other owners.

## Fixed workload and phase

The component route is host `Handles::create` → public `Storage`/Save construction
and `HistoryCatalog::commit_branch` → `Handles::seal`; there is no daemon, SDK,
HTTP, Docker, FUSE or host-mediated runtime in this component control.

- Disposable / WAL / synchronous=OFF explicitly; one construction worker.
- Fresh-output operation: `--setup fresh`; no earlier Store is read or reused.
- Exactly 128 different 32,768-byte inputs, generated by xorshift64 with seed 327
  and shifts 13/7/17, in ordinal order. Fixed warm in-memory fixture in both arms.
  Generate it before the operation timer. There is no file/cache pre-touch.
- The operation timer includes Store creation, stack/genesis and Branch creation,
  all 128 constructions, Save finishes and history publications, and final seal.
  Genesis logical size is zero. Each Commit records one file-root component
  fixture, logical size 32,768 and message `Counter screen`. These artificial C5
  roots are component inputs, not qualified filesystem snapshots.
- The complete child/command wall includes fixture generation and final receipt
  write; wrapper wall includes process launch. Each command has a 15-second wall
  limit. No setup, build or verifier time is subtracted from command wall.
- Each invocation has a fresh Store and append-only receipt path. Retain every
  failure, timeout and ineligible attempt. No retries or unchanged resampling.

`created-in-sample Store; fixed warm in-memory fixture` is the cache contract.
All Store work belongs to the single timed operation. This claims neither cold
storage bandwidth nor independent transfer performance. The two arms use identical
fixture-generation, allocation and cache treatment. Unknown/mismatched cache
state makes the row INELIGIBLE, never PASS.

## Metrics, gates and verifier

Publish operation nanoseconds, complete child and wrapper nanoseconds, sealed
main-file length and allocated bytes (`st_blocks * 512`). Report lifetime child
RSS only if observed, labelled lifetime and never as phase peak. There is no new
memory-flatness qualification in this screen. Raw measurements remain one sample,
not a median or repeatability claim.

The component screen passes only with known complete operations, clean closed
Stores and exact verification, command wall ≤15 s, `on / off` operation time
≤1.15, and `on / off` allocated bytes ≤1.05. Report operands and
`100 * (on - off) / off` for both. A miss is retained and diagnosed from counts
or source, not replaced by a repeated unchanged arm. This is the prospective
accounting-overhead budget; it does not reopen frozen earlier-family gates.

Verification is a separate once-per-arm command, <10 s with an explicit 10-second
wall cap. Reopen explicitly read-only/Disposable, traverse exactly 128 Commit
records with exact messages and logical size, and check the terminal parent.
An independent SQLite reader checks row counts and sums of Commit/Layer logical
bytes, unique canonical locator bytes and pack lengths. `on` totals must equal
those sums; `off` totals remain zero by the declared ablation. Confirm metadata
pack-domain sum and occupied-page overhead, schema/user version, WAL/OFF profile,
file length and allocation. Verification never contributes to speed arithmetic.

Store totals are one fixed-size row. `canonical` counts first-wins locators;
`stored` counts all published pack bodies including race leftovers; metadata
counts metadata-domain pack bytes plus occupied SQLite bytes outside all pack
bodies. Per-Commit newMetadata counts metadata-domain bodies from that Save,
without inventing exclusive per-Commit SQL/index attribution. `file` is committed
logical database pages including free pages and pages currently in WAL, not
main-file or extra WAL allocation. Store logical counts immutable Commit and Layer
records (published Commit and Layer are two saved history states).
